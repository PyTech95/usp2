## 4. Exact failure point
Backend traceback (active run logs):
```
requests.exceptions.HTTPError: 429 Client Error: Too Many Requests for url:
  https://integrations.emergentagent.com/objstore/api/v1/storage/init
  https://integrations.emergentagent.com/objstore/api/v1/storage/objects/uspindia/display/<id>/v1-800
  File "/app/backend/routes_media.py", line 271, in public_image
  File "/app/backend/routes_media.py", line 22, in fetch
  File "/app/backend/core.py", line 139, in init_storage
ERROR: Exception in ASGI application  →  500 Internal Server Error
```

Source (from active run):
- `core.py` `init_storage(force=False)`: caches a process-global `_storage_key`; on a cold pod the key is `None`, so concurrent threads each POST `/storage/init`. `r.raise_for_status()` on a 429 raises.
- `core.py` `_get(path)`: `for attempt in range(2)` — retries ONLY on `status_code == 404`; it does **not** handle 429 and has no backoff. A 429 immediately hits `raise_for_status()`.
- `routes_media.py` `fetch(path)`: per-pod in-memory `_cache` (cap 150). After a republish / new pod the cache is cold, so a homepage's ~6 images fire ~simultaneous `/init` + `/objects` calls → burst → proxy returns 429 → that subset 500s. Already-cached or lucky requests return 200 → intermittent, "some images missing."

Why preview looks fine: long-lived warm pod + single editor → no burst. Production: fresh pod/cold cache after each republish + many concurrent visitors/crawlers → bursts trip the rate limit.

**Failure point = object-storage proxy 429 (rate limit) + app code that does not handle 429.** Not missing data, not auth, not env, not separate DB.

## Recommended fix (Code — E1), no migration needed
1. In `core.py` `_get`/`_put`/`init_storage`: handle HTTP 429 — retry with exponential backoff and honor `Retry-After`; do not let 429 become a 500. (Also map genuine storage-missing to 404, keep 429 as a transient retry.)
2. Serialize `init_storage` with a lock so a cold-start burst shares ONE `/init` call instead of N concurrent ones (and cache/persist the storage key with a TTL).
3. Reduce request volume / smooth bursts: raise cache TTL on `/api/media/...` responses (currently `public, max-age=300`) so Cloudflare/browser cache the derivatives for much longer; optionally warm `_cache` or add a small concurrency limiter around storage fetches.
4. Graceful degradation: on transient storage error, return a 503/placeholder rather than 500 so a single slow image does not surface as a broken page.

If 429s persist even after client-side backoff/caching, the storage-proxy rate limit itself may need raising — that is a Platform/Support item, but the first-order fix is in the app code above.
