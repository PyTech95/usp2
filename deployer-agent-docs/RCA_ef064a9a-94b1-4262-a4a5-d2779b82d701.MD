## Q1 — Object-storage tenant/access: preview vs prod, and the two media GETs

### Storage model (from source, `backend/core.py`)
- Object storage is the Emergent object store at `{INTEGRATION_PROXY_URL}/objstore/api/v1/storage` (falls back to `https://integrations.emergentagent.com` if unset).
- `init_storage()` (core.py:164) authenticates by POSTing `{"emergent_key": os.environ["EMERGENT_LLM_KEY"]}` to `/init` and receives a `storage_key`. **→ The storage tenant/bucket is keyed by `EMERGENT_LLM_KEY`.** `EMERGENT_LLM_KEY` here is doing double duty: it is both the LLM key *and* the object-storage tenant credential — it is NOT a separate storage secret.
- Object paths are namespaced by a **hard-coded** constant `APP_NAME = "uspindia"` (core.py:26) — e.g. `uspindia/originals/<id>/v<n>.<ext>`, `uspindia/display/<id>/v<n>-<w>`. Not derived from DEPLOYMENT_NAME or the DB; identical string in every environment.

### Do preview and prod resolve to the SAME tenant/bucket? — YES (confirmed, no secret revealed)
- `list_secrets(equals={EMERGENT_LLM_KEY: <value from pulled source backend/.env>})` → prod active run returns `matches_expected: true`, `is_empty: false`.
- Therefore prod's `EMERGENT_LLM_KEY` is byte-identical to the source/preview `.env` value → **same Emergent storage account → same tenant/bucket.** Combined with the identical hard-coded `APP_NAME="uspindia"` prefix, **preview and prod read and write the exact same objects.** There is no per-environment isolation of media.
- Implication for your plan: the "portable media fallback if tenants differ" branch is **not needed for this deployment as currently coded** — the tenants do not differ. (Caveat: this holds only while `EMERGENT_LLM_KEY` stays equal across envs and `APP_NAME` stays hard-coded. If the key is ever rotated in one env, or APP_NAME is made env-dependent, the bucket/prefix diverges.)

## Q2 — What does redeploy package: working tree, or committed Git snapshot?

**The `pull_source` step packages the PREVIEW pod's current `/app` working tree — NOT a committed Git snapshot.** It copies `/app` excluding only `node_modules` and `.git`, zips it, and uploads it. It does not run `git` and does not honor `.gitignore`.

Consequences for your design:
1. **Uncommitted / untracked files in the preview workspace DO travel.** A `backend/content_release.json` baked fallback is included in the bundle **iff it exists in the preview pod's `/app` at the moment the deploy is triggered** — commit status is irrelevant.
2. **JSON written by CMS API requests against the LIVE PRODUCTION app will NOT travel.** Those writes land on the production pod's filesystem (ephemeral) and/or object storage + the prod Mongo DB — **not** in the preview pod. The next redeploy pulls from *preview*, so prod-runtime JSON mutations are never recaptured into the bundle, and the freshly built immutable image would not contain them.
3. **The deployed image is immutable; pod-local writes in prod are lost on next deploy/pod restart.** Durable CMS state must live in Mongo (prod DB `usp-india-cms-test_database`, 11 collections incl. `pages`, `media`, `revisions`, `enquiries`, `users`) and/or the shared object storage — both persist across republishes. A JSON file on the pod does not.

**Guarantee you asked for:** the source bundle travels with every republish, and it is the preview working tree in full. But it only guarantees travel of files that exist *in the preview workspace*. To make `content_release.json` travel deterministically, it must be written into the preview `/app` (and included in the git checkpoint/workspace) before republish — not produced solely by the production CMS at runtime.

> Side note: the guarded-release machinery you described (DB-generated environment identity, `content_deployment.json`, latest-pointer manifests, idempotent checksum import) is **not present in the currently deployed source** — `backend/content/` holds only `rakhigarhi_reference.json`, and there is no `content_release.json`/`content_deployment.json` or env-identity code yet. The only `manifest.json` reference is inside the admin export/import zip in `routes_admin.py`. So this is greenfield — build it against the facts above.
