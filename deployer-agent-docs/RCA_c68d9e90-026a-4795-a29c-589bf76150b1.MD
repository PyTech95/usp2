# RCA — Images missing on production (quick-deploy-375)

## Problem statement
On the live site (https://quick-deploy-375.emergent.host) images are broken/empty while text/layout render fine. The same pages show images correctly in the Emergent preview.

## Investigation & evidence
1. **Secrets are fine.** `list_secrets` on the active run shows both `EMERGENT_LLM_KEY` (is_empty=false) and `INTEGRATION_PROXY_URL` (is_empty=false) present and non-empty. Backend logs confirm `usp - INFO - Object storage initialised` — so `init_storage()` authenticates to Emergent Object Storage successfully in production. **Storage auth is NOT the cause.**

2. **Live media endpoint returns a 404 from the APP (not infra).** `GET /api/media/6fc82b55f714459f9499182413231bbb/800` → HTTP 404, content-type `application/json`, body `{"detail":"Not found"}`. This is the FastAPI route's own "Not found", i.e. the media doc lookup/approval check failed — not a CORS/routing/nginx problem.

3. **Root cause — the media doc does not exist in the production database.** `mongo_query` on the prod DB (`quick-deploy-375-test_database`), collection `media`:
   - `count {id: "6fc82b55f714459f9499182413231bbb"}` → **0** (the id the preview page references).
   - Total media docs = 40, but their ids are completely different (`be8353f023284c8ebc7228e9189bf5f9`, `1877001f58894d9dac1da0559bca8a3a`, `bbd61e5bccef4483ba17408d5e1abf8d`, …).
   - The prod `home` page content (`GET /api/public/pages/home`) still points its hero at `"image":{"media_id":"6fc82b55f714459f9499182413231bbb","media":null}` — a media_id that has no matching document in the prod `media` collection.

4. **Storage namespace is reachable and correct for docs that DO exist.** `GET /api/media/be8353f023284c8ebc7228e9189bf5f9/800` (an id that exists + is approved in prod) → **HTTP 200, image/jpeg**, real JPEG bytes streamed. This proves production CAN read binaries from Emergent Object Storage. So the bucket/namespace is fine; the problem is strictly missing/mismatched DB records.

## Conclusion
This is a **data divergence between preview and production**, NOT a secret, code, storage-namespace, or routing problem. Redeploys do NOT migrate database data, so the prod DB still reflects an older/out-of-sync snapshot in which page documents reference `media_id`s that were never written into prod's `media` collection (and vice-versa — prod media carries ids preview no longer uses). Every public page whose referenced `media_id` is absent in prod resolves `media:null` and the image renders broken.

A redeploy was performed per user request (run c68d9e90) — it went live cleanly, but as expected it did NOT fix the images because the cause is data, not code/build.

## Fix
- **User (change_mongo_data):** Re-sync production data with preview using the DB Manager (preview → prod copy) so the `pages` documents and their referenced `media` documents are consistent. Confirm afterward that `/api/media/6fc82b55f714459f9499182413231bbb/800` returns 200 image/jpeg on the live domain. Alternatively, re-save/re-publish the affected pages in prod so they reference media_ids that actually exist in the prod `media` collection.

## NOT the cause (ruled out with evidence)
- Secrets missing/empty — ruled out (both present; storage initialised).
- Object Storage namespace/credentials — ruled out (existing approved media streams 200 image/jpeg).
- CORS/routing for /api/media/* — ruled out (route returns a clean app-level JSON 404, and a valid id returns 200).
